The Chalk Toss — how a question becomes an answer

The model writes the query and describes the rows. Every number comes from D1 in between; it is never asked to recall one. One validator sits on every path — including the ones with no model in them at all.

Request path — left to right, one question. Dashed boxes can be skipped.
1 Client The question Three kinds now: a browser, a script with an API key, or an AI agent over MCP.
2 access.js · limiter Who's asking, and can they afford it API key → 2h session → Turnstile, in that order; the first Turnstile pass mints the session, so one challenge per visit. MCP has no human to challenge, so a Durable Object meters it instead: 20/hr per IP, 150/day global.
3 Vectorize Seen this question before? Embeds the question and looks for a near neighbour. Caches SQL, never answers — so a hit still re-queries D1 and reports today's rows.
4 Gateway → Workers AI Writes SQL qwen2.5-coder-32b, temperature 0. Asked for a statement — never an answer. skipped on a cache hit
5 Guard Validates the SQL Allowlist with a preprocessing pass. Every path converges here — generated, cached, or written by the caller. 15 tests.
6 D1 Runs it, returns rows The only source of any figure the user sees. Nothing downstream can alter a number.
7 Gateway → Workers AI Describes the rows llama-4-scout-17b, streamed token-by-token. Only ever sees a non-empty result set. Dates and team names are formatted in code first, so it copies — never converts. skipped for raw-data callers
8 Client Answer + query + rows + chart The prose never appears alone. The reader — human or model — can always check it against its source.
⟶ cache hit rejoins at the guard
Skips the SQL model entirely — the single most expensive step. The cached statement is guarded exactly as a fresh one is; approval once is not approval forever.
⟶ MCP · run_stat_query enters here, at step 5
The caller's own model writes the SQL and our guard decides whether it runs. No inference on our side at all — this path never touches an orange box. It is the cheapest route through the system and also the most capable one, which is only possible because the validator distrusts every source equally.

Why the cache is safe

storesSQL, never the answer
becauseData updates nightly — a cached answer becomes a confident lie
threshold0.92 cosine, chosen by measurement
the findingThe loosest paraphrase (0.863) scores below every near-miss (0.878–0.896) — the classes overlap, so no cutoff catches them all
soTuned to prefer a miss. A miss costs Neurons; a bad hit costs correctness.

Reading the colours

Model involved — output untrusted until validated Ground truth — numbers originate, or SQL is replayed into it Platform — Worker, routing, client Refusal — stops rather than guesses
The cache is teal, not orange. It stores a statement, not a sentence — so a hit never puts model output in front of a reader. D1 re-runs it either way.

Grounding a model in a datastore prevents invented numbers. It does not prevent a wrong query from producing a confidently wrong answer — which is why the validator, not the model, is the load-bearing part.

"How many MVPs did he win?" once returned 0 — the awards column existed but was empty, so the query succeeded and produced a real, meaningless figure. An empty column is more dangerous than a missing one, because an empty column answers. That guard was written to contain our own model. It turned out to contain anyone's — which is the only reason a public endpoint that runs caller-written SQL is a reasonable thing to publish rather than a reckless one.
